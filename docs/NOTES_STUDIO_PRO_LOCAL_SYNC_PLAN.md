# Notes Studio Pro: private local-network sync

This document is the implementation checklist and security boundary for the Pro-only sync work. It is not a separate UI module. The user authorized changes to Notes Studio Pro; Notes Studio, Notes Workspace, and Sheets sync remain untouched.

## Goal

Keep Notes Studio Pro available offline on the laptop and S25 Ultra, then exchange edits directly when both devices are online on the same Wi-Fi or S25 hotspot. Do not use an AI API or third-party note-content storage for this mode.

## Audited starting point

- Pro stores notes in browser `localStorage`, keyed by title; no Dexie/IndexedDB, encryption, or sync existed.
- The production server served static files only (`GET`, `HEAD`, `OPTIONS`).
- The laptop is using the S25 hotspot, as confirmed by the user. Windows exposes the link as a generic Wi-Fi adapter. The laptop had IPv4 `10.25.29.200` and gateway `10.25.29.157`; the sandbox could not query the detailed Windows network profile or access the S25 to test reverse reachability.
- The phone can keep using its last local copy with the laptop off. A direct sync only transfers changes when the laptop sync server is running and both devices can reach it.

## Current implementation

- `npm run serve:notes-sync` opts into the sync endpoint. Normal `npm run serve` remains static-only.
- The endpoint is `PUT`/`GET /api/notes-studio-pro/sync`, accepts private-network peers only, requires a pairing token stored in the current Windows user's app data, limits request size, and uses version checks. The token is used as an HMAC-SHA256 signing key and is never sent over HTTP. Signatures cover the method, route, timestamp, nonce, `If-Match` version, and body hash; short-lived timestamps and one-time nonces reject replays. The latest 12 encrypted snapshots are retained; a stale version gets `409` instead of overwriting a newer version.
- The first implementation uses one shared pairing token for this Pro sync set, not separate per-device credentials. Rotating the token revokes access for all paired devices, which then need to be configured again.
- Pro adds stable IDs for existing title-keyed notes, unique names for new notes, and a sync dialog. It encrypts the full notes snapshot in the client with AES-GCM; the key comes from a shared passphrase using PBKDF2. The passphrase is not saved. A local HMAC hash map lets the client detect same-note offline edits and create a conflict copy instead of silently dropping either edit.
- The service worker bypasses this API route so it cannot return a cached snapshot.

## How to start a manual sync session

1. On Windows, run `npm run serve:notes-sync` from the app folder. This starts the production app and the opt-in sync endpoint; closing the terminal stops sync.
2. Keep the laptop's existing Pro source page open on its original origin (for the current session, `http://localhost:5173/?view=notes-pro`). In the Sync dialog, enter the current laptop hotspot IP and `/api/notes-studio-pro/sync`, the pairing token from the protected file, and a shared passphrase of at least 12 characters. Do not open a new app origin expecting it to contain the same local notes.
3. On the S25, use the installed Om Knowledge OS app (not Chrome at the laptop's plain-HTTP IP, because that page lacks secure WebCrypto). Enter the same laptop URL, pairing token, and passphrase.
4. With both devices on the S25 hotspot and the laptop awake, sync in this order: laptop → S25 → laptop. The first pass uploads the laptop's notes. The phone pass merges the laptop snapshot with phone-local notes and uploads the merged set. The final laptop pass pulls any phone-only notes into the laptop's local store. Repeat this sequence after later edits; sync is user-triggered in this first version.

`npm run cap:sync` updates the Android project assets but does not build or install the Android app. The `deploy:s25` command performs those remaining steps.

## Recovery and credential rotation

- If one device is lost or its app storage is cleared, install the updated app on that device and sync it from a working device using the same pairing token and passphrase. The laptop must be running the sync server. Only the latest successful sync can be restored; edits that existed only on a lost device were never transferred and cannot be recovered from this server.
- If the passphrase is forgotten, do not clear the local Pro notes on either device. The server snapshot cannot be decrypted without it. Use a device that still has the notes, export a JSON backup, choose a new passphrase, and create a new sync set from that device. The existing encrypted server history remains unreadable under the new passphrase.
- To rotate a lost/compromised pairing token, stop the server, remove `pairing-token.txt` in the printed app-data folder, and restart `npm run serve:notes-sync`. The server generates a new token; re-enter it on every device. The encrypted note history is retained.
- The server keeps the newest 12 encrypted snapshots. For a separate encrypted file backup, stop the server and copy `vault-encrypted.json` from the same app-data folder to a protected backup location. The file is ciphertext, but it is still sensitive metadata and should be stored privately. The Pro UI does not yet offer selection/restoration of an older server snapshot.
- Keep the existing Pro JSON export as a recovery copy in a protected location. That export is plaintext unless the user encrypts the file separately. If both devices and all exports are lost, the encrypted server snapshot alone is recoverable only with the original passphrase.

## Privacy boundaries and known limits

- The sync server stores ciphertext, not note text. Pro's working copy is still plaintext in each device's `localStorage`; this feature does **not** encrypt notes at rest on the laptop or phone.
- The pairing token is saved in each paired browser's local storage. The shared encryption passphrase is entered for each sync and cleared from the input afterward; it is not saved by this feature. The token is not sent on the network: clients sign each request with HMAC-SHA256. This protects request integrity and blocks ordinary replay while the server is running, but it is not TLS and does not hide traffic size/timing. The note contents remain AES-GCM encrypted, and the server stores ciphertext only.
- Secure browser cryptography is required. On the laptop, `localhost` is secure. On the S25, use the installed Capacitor app or an HTTPS origin; a PWA opened from `http://<laptop-lan-ip>` is not allowed to use WebCrypto and Pro blocks sync there rather than downgrading encryption.
- The Android app manifest allows cleartext connections so the app can reach the laptop's private IP. Pro's sync UI restricts HTTP URLs to loopback/private IPv4 addresses; the endpoint independently rejects non-private peers. Note payload confidentiality comes from AES-GCM and request integrity from HMAC, not transport TLS. The cleartext permission is app-wide at the Android network layer, so do not add arbitrary public HTTP sync targets.
- Same-network sync does not require internet or hosting, but the laptop must be awake and the endpoint running. To fetch new laptop edits while it is off, an always-on home host or hosted encrypted store is still required.
- Android background sync is not promised. Initial behavior is user-triggered while Pro is open.
